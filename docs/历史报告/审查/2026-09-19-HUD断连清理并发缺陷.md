# HUD 断连清理并发缺陷（退出世界 ConcurrentModificationException）

> 触发：真实机报错栈（GTNH 1.7.10 + lwjgl3ify 3.0.20，`qz_uilib-4.11.0-4-0.38+a2300a1b47-dirty-dev.jar`）。
> 方式：Lead 读码定位根因 → 最小修复 → 完整 build → 零上下文子代理两组独立复核 → 处置 → 复跑 build。
> 结论：**根因是跨线程访问，不是同线程重入**。修复点在调用方（网络线程必须派发到客户端主线程），
> 状态持有方补线程契约断言与结构性加固。

## 一、根因（证据链逐条可复核）

### 1.1 保留窗口表只在宿主内部被写，且抛点紧邻清空

`SceneHudHost.retained` 的写点全仓只有四处（`grep` 可复现；行号为**修复前**）：

| 位置（修复前） | 操作 | 线程 |
|---|---|---|
| `SceneHudHost.render` :95 / :101 | `retained.remove` / `retained.put` | 渲染帧（客户端主线程） |
| `SceneHudHost.disposeInactive` :277 | `retained.remove`（已先取 keySet 快照） | 同上 |
| `SceneHudHost.clearWorld` :267-268 | 迭代 `values()` + `retained.clear()` | **入口不固定** |

抛点在 :267 的迭代上，紧邻的 :268 就是 `retained.clear()`——即「迭代未结束，表被清空」。
（4.8.0 时代的同形状崩溃栈里，同一行是 :252，见 §1.5。）

### 1.2 排除同线程重入

- `clearWorld` 的两条合法入口都在客户端主线程：`UiHudRenderListener.onWorldUnload`（`WorldEvent.Unload`）与断连派发后的主线程任务。
- `render` 的唯一入口 `UiHudRenderListener.renderHudFrame` 由 `RenderGameOverlayEvent.Post` 驱动，也在客户端主线程；
  `Minecraft.loadWorld` 执行期间不会重入渲染事件（渲染事件只在 `runGameLoop` 的渲染阶段 post）。
- `clearWorld` 循环体只调 `window.dispose()` → `SceneHostWindow.dispose` → `SceneHostAssembly.detachTree` + `SceneRuntime.dispose`
  → `Owner.dispose`：全 `src/main` 无任何 `EVENT_BUS.post`（仅 3 处 `register`），**仓内不存在把清理再入回宿主的事件路径**。
- 因此写者不在主线程：`HashMap` 的 fail-fast 迭代器只在「迭代期间结构被改」时抛 CME。

### 1.3 唯一的跨线程写者：`ClientProxy.onClientDisconnect`（修复前 :132-138）

```java
@SubscribeEvent
public void onClientDisconnect(FMLNetworkEvent.ClientDisconnectionFromServerEvent event) {
    try {
        uiHudRenderListener.clearWorld();   // ← 直接调用，未派发
    } catch (RuntimeException exception) {
        MyMod.LOG.warn("HUD 断连清理异常", exception);
    }
```

同一个方法里，**既有代码已经写明这个事件在网络线程触发**（修复前 :157 的注释）：
「本事件在网络线程触发，而 SPI 全方法只允许客户端主线程（ADR A-01）⇒ 先派发到客户端主线程队列」——
候选源 SPI 的释放照此派发，**HUD 宿主与渲染分级表两处漏了同一处理**。

断连事件确由网络线程发出：`NetworkDispatcher.disconnect/close`（Netty `ChannelHandlerContext` 回调）直接
`bus().post(new FMLNetworkEvent$ClientDisconnectionFromServerEvent(manager))`；真机 `fml-client-1.log` 显示
客户端 FML 握手在 `[Netty Client IO #0]`。

### 1.4 复现时序

```
主线程（runTick）                          网络线程（Netty）
Minecraft.loadWorld(null)
  └ WorldEvent.Unload
      └ SceneHudHost.clearWorld
          └ for (retained.values()) …       ← 迭代中
                                           ClientDisconnectionFromServerEvent
                                             └ ClientProxy.onClientDisconnect
                                                 └ SceneHudHost.clearWorld
                                                     └ retained.clear()   ← 表被清空
          └ 迭代器 next() → ConcurrentModificationException
```

两条路径的时间窗重叠，故表现为「退出世界偶发崩溃」而非必现。

## 二、同类缺陷（同一根因族，一并处置）

`ItemRenderTierRegistry.invalidateAll("client_disconnect")` 在同处网络线程被直接调用，而该类 javadoc 明文规定
「写路径（`classify`/`invalidateAll`）只允许客户端主线程」。分级表用 `ConcurrentHashMap`，不会抛 CME，
但**失效广播的监听器会在网络线程执行**（宿主 UI 代码被跨线程回调），同属违约。

`DocumentRemoteImageCache.clear()` 只做 `entries.clear()`（ConcurrentHashMap、无 GL、无线程契约），保持网络线程同步执行（更快释放）。
`VanillaConnectionLifecycle` / `ForgeConnectionLifecycle` 的断连处理只清各自网络层握手表，属网络线程合法范围。
`MixinNetHandlerPlayClient` → `VanillaMixinTransport` → `NetService.onClientDisconnected` 只动网络层注册表，不触碰 HUD。

## 三、处置

### 3.1 调用方（根因修复）：`ClientProxy.onClientDisconnect`

HUD 清理 + 渲染分级表失效合并为**一个**客户端主线程任务派发，与同方法内候选源 SPI 释放同口径：

```java
MainThreadDispatcher.getInstance().enqueue(NetSide.CLIENT, new Runnable() {
    @Override public void run() {
        try { uiHudRenderListener.clearWorld(); } catch (RuntimeException e) { … }
        try { ItemRenderTierRegistry.invalidateAll("client_disconnect"); } catch (RuntimeException e) { … }
    }
});
```

延后一拍不会漏清理：断连后主菜单照常 tick，`ClientTickEvent`（`ForgeMainThreadDispatcherBridge`）排空通道继续运行
（`Minecraft.runTick` 调 `FMLCommonHandler.onPre/onPostClientTick`，后者发出 `TickEvent$ClientTickEvent`）；
期间 `minecraft.theWorld == null` ⇒ `visible()` 恒 false，HUD 不绘制。`enqueue` 在客户端侧不被拒。

### 3.2 状态持有方：线程契约显式化 + 结构性加固

1. **新增 `client/hud/HudClientThread`**（包内）：HUD 域「客户端主线程」契约的单一判定源。判定口径与
   `MinecraftMainThreadOracle` 同源（1.7.10 原版 `func_152345_ab`）。无客户端运行时（headless 单测 / 服务端 JVM）
   时放行并按站点留一条 WARN；其中「Minecraft 类不可用」判定一次即**永久短路**（类初始化失败在 JVM 内粘性，
   反复探测只会重复抛错——对齐踩坑记录「headless 测试不能触 Minecraft 类初始化」），「实例尚未建立」不短路。
2. **`SceneHudHost.render`（修复后 :78）/ `clearWorld`（:284）入口断言**：把「静默并发破坏」变成带站点的明确异常，
   不再表现为无关位置的 CME 或表损坏。
3. **`SceneHudHost.clearWorld` 改为逐个「摘账 → 释放」**（修复后 :283-305）：
   - 先 `retained.remove(id)` 再 `dispose()` ⇒ dispose 期间 mod 回调重入宿主时，表内不会出现「正在释放的窗口」，
     迭代也不再因回调修改而失效（修复前重入路径还可能取出**已 dispose 的窗口**成帧 → 用已释放 runtime）；
   - 单个窗口释放失败**不短路其余窗口**：全部尝试后把首个失败作为主异常、其余作为 suppressed 统一重抛
     （对齐仓内 `appendFailure` 口径）。若失败即中断，已摘账窗口会连同剩余窗口一起失去释放机会——这是复核指出的
     原始「先快照清空再逐个释放」写法的真实缺陷，本批已修正；
   - 二次 `clearWorld` 幂等（表已空），并顺带消除「同一窗口被 dispose 两次」。
4. **`ClientHudServiceImpl` 删除第三份线程判定拷贝**，委托 `HudClientThread`：异常消息与 headless 告警文案逐字不变，
   告警由「每次调用一条」降为「每站点一条」（渲染路径每帧断言，必须去重）。
5. 顺带修正两处指向已删方法的过时引用（`MinecraftMainThreadOracle` 的判定源交叉引用、`GlAttribDepth` 的 warn-once 先例现址）。

### 3.3 新增源码结构守卫（补上「无可红测试」缺口）

`src/test/java/club/heiqi/uilib/client/hud/HudThreadContractGuardTest.java` 三条断言：

| 用例 | 钉住的契约 |
|---|---|
| `disconnectCleanupRunsInsideClientMainThreadDispatch` | `ClientProxy.onClientDisconnect` 的 HUD 清理必须落在 `enqueue(NetSide.CLIENT, …)` 的派发块内（花括号配平取块） |
| `hostStateEntryPointsAssertClientThread` | `SceneHudHost.render` / `clearWorld` 方法体必须含对应站点的 `HudClientThread.assertCurrent(...)` |
| `hudThreadCheckHasSingleSource` | 线程判定只有一处来源：服务实现必须经 `HudClientThread`，且不得再出现 `func_152345_ab` |

行为测试守不住这个缺陷（headless 下断言按设计放行、并发窗口不可复现），故按仓内既有范式（`PickerSourceGuardWiringTest`）用结构守卫钉死。

## 五、未覆盖 / 待复核

1. **并发修复的最终证据仍来自真机**：headless 单测无法覆盖真实并发路径（断言按设计放行）。
2. **外部 mod 的 runtime dispose cleanup 再入宿主**：仓内无此路径，但下游 mod 的 `Owner` cleanup 回调若再入 HUD 宿主，
   属本次未覆盖的替代解释（低概率；§3.2-3 的结构改动已让重入不再破坏迭代与窗口账目）。
3. **`HudToolbarService` / `HudScaleState` 的主线程契约无断言**（javadoc 声明了但实现未校验）：
   其写路径经 `Signal.set → ReactiveScheduler.queueWrite` 的无锁 `LinkedHashMap`，外部 mod 跨线程写会炸在调度器队列而非 HUD 宿主。
   **建议处置、待裁定**——本批未动，因为它会改变公共写面的行为（违约从静默变为抛异常）。
4. **`ItemRenderTierRegistry` javadoc 与实现的落差**：javadoc 声明写路径限主线程，实现无断言（`ui.scene.image` 不宜反向依赖 `client.hud`）。
   本批已把生产侧违约调用点（网络线程）收口，落差本身登记待裁定。
5. **分级表失效延后一拍**：断连到下一个 `ClientTickEvent` 之间存在 ≤1 tick 的「旧分级可见」窗口（无实质影响：CHM 读、且旧结论只是保守回退）。
6. `SceneHudHost.disposeInactive`（render 帧内注销清理）仍是「`remove` 后直接 `dispose`，失败即中断本帧」——既有行为，非本次引入，未改。
7. 矩阵栈插桩（约 15 处）等 GL 自净审查挂账项与本次无关，仍见 `2026-09-19-GL使用自净审查.md`。

### 6.3 未采纳建议与理由（如实登记，供裁定）

- **注入式判定接缝（审核 B-6/建议 3）未采纳**。理由：①生产只有一种判定实现，注入层在生产侧无实际收益，
  属「纯测试便利」；②仓内已有先例 `LanguageEpochService`（同样 `catch (Throwable)` + 注释说明 headless 失败）
  说明该形态被接受；③改用的「粘性短路」把踩坑影响压到「每 JVM 一次、且被捕获」，并让探测不再逐帧重复。
  代价：headless 测试 JVM 仍会发生一次 `Minecraft` clinit 失败（粘性），这一点如实记录；若要求「零触碰」，
  则必须引入测试接缝（`PickerSourceGuard` 范式）并让 `SceneHudPipelineTest` 装配注入。
- **`HudToolbarService`/`HudScaleState` 补断言未采纳**：会把「外部 mod 跨线程写」从静默变成崩溃，属公共行为变化，
  需用户裁定后再做（§5-3）。

## 七、真机排查入口（若仍复现）

1. 取崩溃栈顶是否仍为 `SceneHudHost.clearWorld`：若是，读 WARN/ERROR 里的**线程名**（`Client thread` vs `Netty …`）。
2. 若出现 `HUD register/close must run on the client main thread` 或 `SceneHudHost.render/clearWorld must run on the client main thread`：
   说明仍有非主线程入口——按异常站点名直接定位调用方（这正是本次断言的用途）。
3. 若出现 `线程校验被跳过（Minecraft 不可用，headless 环境）：<cause>`：记录 cause，说明探测路径本身失败（生产不应出现）。
